# Browser Game Runtime Comparison

**Decision:** Use Phaser 3 for the proposed first **top-down 2D scene game**, subject to a short proof of concept and team/supervisor review. This is a requirements-based choice, not a measured performance result. The runtime should execute a **validated, versioned game specification and approved assets**; the AI service should not supply executable JavaScript to the browser. The first action set proposed in `docs/decisions/scope-and-contract.md` is movement in a bounded scene, inspect, collect, interact, dialogue choices and an explicit goal. These remain a design proposal until agreed.

## Criteria and alternatives

| Criterion | Phaser 3 | PixiJS 8 | Godot 4 web export |
| --- | --- | --- | --- |
| 2D mechanics | Dedicated browser game framework with Scenes, input, animation and built-in Arcade/Matter physics; suitable for the proposed bounded top-down scene and movement/interact/collect rules. [1–3] | Strong 2D rendering, scene graph, ticker and pointer events. It is a renderer rather than a full game engine; game rules, collisions and orchestration need our own code or added libraries. [4–6] | Full 2D engine with scenes, physics and editor. Its built-in breadth is attractive for complex authored games, but more than the initial browser runtime needs. [7, 11] |
| Load a structured specification | Phaser Loader accepts JSON and assets; our adapter must validate and map fields to a fixed set of Scenes, entities, rules and win states. JSON loading is built-in, but the **game schema and adapter are ours**. [2, 3] | Assets can load JSON/assets. The adapter and most gameplay systems would be ours; this gives flexibility at additional implementation cost. [5, 6] | A prebuilt exported Godot game can load runtime data/JSON and construct game nodes under its own rules. Web export is a bundled project; integrating newly generated data requires an explicit data handoff and runtime loader. [7, 8] |
| Player input and completion | Keyboard/pointer input and scene lifecycle are available. We must implement goal checks, loss/restart and an ending screen explicitly. [2, 3] | Pointer/touch interaction is available; keyboard controls and goal checks need application code. [5, 6] | Input and game state are engine features, but our specific genre rules and completion logic still need implementation. [11] |
| Browser preview and integration | Runs as a JavaScript game inside the web client, with Canvas/WebGL browser rendering. A fixed runtime can load a per-project specification for preview without building a new game binary. [1–3] | Also a JavaScript browser rendering stack, easy to embed in a web page; the missing game systems increase first-prototype work. [4–6] | Produces web export files for a web server; Godot 4 web rendering requires WebGL 2. Threaded exports need cross-origin isolation headers, although single-thread export is available. Embedding and per-project delivery need extra integration decisions. [7] |
| Safety boundary | Runtime choice does not make model output safe. Accept only schema-validated data and allowed assets, escape displayed text, and serve previews with an appropriate origin/CSP or sandbox policy. Do not evaluate generated code. [9, 10] | Same boundary; a custom rules layer raises the amount of code to audit. [9, 10] | Same boundary for untrusted story and asset data; do not treat an engine export as a security sandbox for arbitrary generated scripts. [9, 10] |

## Recommendation and implementation boundary

Phaser 3 is the most direct match for the proposed 2D web prototype. Its documented scene lifecycle, input, JSON asset loading and simple physics permit a **fixed, auditable runtime**. The AI pipeline can generate game data conforming to a versioned schema; the client maps that data onto supported mechanics. An unsupported rule should fail validation or be deliberately simplified and shown to the author. This is preferable to assuming the model can generate a new executable Phaser program safely and reliably. [1–3, 9, 10]

PixiJS is a good fallback if the game is mostly a custom visual narrative and we want exact control over a small rules system, but it shifts more work to the team. Godot is attractive if later work demands deeper editor tooling and reusable 2D scenes; its web export and runtime data integration should first be tested in the intended hosting environment. No option alone proves that a generated game can be completed. That requires a schema with explicit goals and a test that reaches the ending.

**Proof of concept after the contract is agreed:** load one handwritten JSON specification, render a bounded top-down scene, move the player, inspect/interact with an object, collect an item, trigger a declarative goal, show an ending screen and restart. Then load an invalid specification and show a controlled error. Verify in the browsers the team intends to support. Record load time and artifact size instead of asserting unmeasured speed or size advantages. Reconsider the decision if these agreed actions cannot be represented without a disproportionate custom engine layer. Platformer, racing and card-game mechanics are not claimed as part of this first slice.
