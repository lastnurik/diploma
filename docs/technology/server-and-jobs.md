# Server Platform and Generation Job Execution

**Decision status, October 2026:** Provisional comparison. The platform must store projects and versions, expose an API to the browser, start generation without holding an HTTP request open, report progress and errors, and publish only validated game artifacts. Generation is proposed as a separate Python component. The alternatives below are feasible designs, not measured benchmarks or an implemented stack.

## Decision criteria

1. **Project API and data:** typed request/response handling, PostgreSQL persistence of project/version/generation records, and integration testing.
2. **Long-running jobs:** a durable handoff to a worker, explicit queued/running/succeeded/failed states, bounded retries and timeouts, and a way to recover from worker failure.
3. **Module boundary:** stable message or HTTP contract between the platform and the Python AI generation component; jobs should be idempotent for the same generation ID.
4. **Delivery and safety:** store validated artifacts separately from untrusted input; the API should serve only published versions through controlled routes.
5. **Team and delivery effort:** fit with Aldiyar’s Java/Spring experience and Nurgeldi’s Python AI work, plus the number of services the team must run and document by the later implementation milestones.

## Recommendation and implementation conditions

**Recommend A for the planned implementation**, subject to a small integration spike and team agreement. Spring Boot fits the designated platform owner, while the Python worker preserves the AI owner’s separate module. RabbitMQ provides a documented cross-language messaging boundary. This choice is based on project fit and traceability, not a claim that it is faster or inherently more reliable than B or C. B remains the simpler fallback if the team cannot run and test the two-language workflow on schedule. C is reasonable but has the weakest fit with the assigned platform owner.

Define the minimal contract before coding: request `{generation_id, project_version_id, spec_version, story_ref, parameters}`; response/result `{generation_id, status, artifact_ref?, simplifications?, error_code?}`. The exact fields, privacy treatment, and where the story is stored must be agreed in the scope-and-contract task. The browser receives a generation ID immediately, then reads the status endpoint; it never waits for model output in the original request. Persist state transitions in PostgreSQL, with unique generation IDs and version checks. On a duplicate delivery, return or reuse the recorded result rather than publish a second version. Keep artifacts unpublished until validation and safety checks pass. Distinguish a model-invalid output from a transient service failure so that retries do not repeat permanently invalid requests.

**Risks to verify in the integration spike:** (1) a job is not lost if database creation succeeds but queue publication fails; use an outbox or another tested reconciliation mechanism if needed, (2) a worker killed mid-job leads to a bounded redelivery without duplicate publication, (3) exhausted retries create a visible failed state and traceable error, and (4) one Docker Compose command starts API, broker, database and Python worker. Record actual timings and behavior later; none have yet been measured.
