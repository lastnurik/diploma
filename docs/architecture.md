# Draft Component Architecture

**Status, October 2026:** Proposed architecture. The [editable component diagram](../diagrams/component.mmd) and [SVG export](../diagrams/component.svg) depict the intended first executable slice, not a running system. The design follows the [scope contract](decisions/scope-and-contract.md) and [platform](requirements/platform.md), [generation](requirements/generation.md) and [frontend](requirements/frontend.md) requirements. Named technologies are provisional alternatives discussed in the [technology comparison](technology-comparison.md).

## Intended result and initial boundary

The [proposal](proposal.md) targets an author entering a game idea/story and receiving a playable 2D browser game with a start, meaningful state-changing actions and a visible ending. Under the proposed data-driven approach, approved game data and assets run through a maintained runtime; a new executable build per story is not required. A specification or synopsis alone is not the playable result. The first bounded scene-game family does not imply support for arbitrary platformer, racing or card mechanics.

## Components and ownership

| Diagram ID | Component and proposed owner | Interface and responsibility |
| --- | --- | --- |
| `UI` | Browser authoring client; M/frontend | Submit bounded story and parameters, poll job, list immutable versions, display safe errors and disclosed simplifications. It never treats a submitted request as ready merely because the HTTP call returned. |
| `RT` | Trusted 2D runtime; M/frontend | Interpret a validated, immutable specification with the supported move/inspect/collect/interact/choose actions; apply state transitions and emit start/progress/ending events. Render generated text as text. No model-generated JavaScript is executed. |
| `API` | Authenticated project/status API; A/platform | Authorize each project/version/job operation, validate request shape, expose draft endpoints in `requirements/platform.md`, return IDs and `queued` promptly, then return canonical state from the database. Only `ready` versions get a playable reference. |
| `JOB` | Job coordinator and recoverable publication; A/platform | Create a distinct version and job, persist the handoff intent, publish a versioned request to the broker, recover an interrupted publication. The outbox is a **proposed mechanism**, not an implemented guarantee. |
| `DB` | PostgreSQL; A/platform | Canonical project owner, original input, immutable version reference, job state/timestamps, validation outcome, artifact metadata and correlation/audit events. Private story and diagnostics do not enter public responses or ordinary log messages. |
| `MQ` | RabbitMQ; A/platform infrastructure | Carry generation request and candidate result/failure events across Java/Python modules. Acknowledgment/redelivery can duplicate work, so generation IDs and publication must be idempotent; broker state is not the client-visible source of truth. |
| `AI` | Python generation worker; N/AI | Extract genre intent, goal and actions, map to the bounded mechanics, build candidate specification, perform bounded repair/checks, return candidate and findings or classified failure under supplied IDs. The platform still independently gates publication. |
| `MODEL` | Optional external provider | Supply untrusted model output. Provider selection and the exact minimum sent story context need a privacy/technology decision. A deterministic/manual candidate could bypass this component. |
| `GATE` | Result validator and publisher; A/platform with N contract | Match generation/project/version IDs and schema major; check strict schema, references, action vocabulary, asset policy, safety and agreed launch/ending verification. On success, save immutable approved data and atomically associate the version with the artifact and `ready` state. On error, record a class and safe `failed` message, without publication. |
| `STORE` | Private artifact storage; A/platform | Hold approved game data and allowed asset references keyed by an immutable version/artifact ID. The exact storage product and atomic publication procedure are open decisions. |
| `ART` | Controlled artifact route; A/platform | Recheck authorization, `ready` status, artifact ownership/version, approved type and path; deliver only approved data/assets and the separately maintained trusted runtime bundle with restrictive response types and `nosniff`. |

The `AI` checks are useful feedback for repair, but its result is still untrusted at the `GATE` boundary. The diagram's self-loop on `GATE` denotes the ordered validation stages, not recursive or unlimited validation.

## Request, result and failure paths

1. `UI` submits a story and parameters to `API`. After authentication and input checks, `API`/`JOB` create a project version and generation ID, persist `queued`, and return those IDs. The proposed request event carries generation ID, project version ID, specification contract version, input reference and parameters; the worker does not own the platform record.
2. `JOB` publishes to `MQ` after a recoverable persisted handoff intent. `AI` consumes the request, optionally calls `MODEL`, creates a candidate game specification and sends a versioned result event. The platform must persist `generating` when the worker starts, using an idempotent status event or equivalent agreed mechanism; the exact event contract remains open. The original and generated content stay within their intended trust boundary; provider output is never browser code.
3. `GATE` processes the candidate and changes `generating → validating → ready` only after all required checks and immutable artifact publication succeed. Exact transaction/storage ordering must be specified and tested so `ready` cannot point to a missing or foreign artifact. `API` polling reads `DB`, returning stage, timestamps and safe message; a ready version also exposes simplifications, instructions and the approved artifact reference.
4. `UI` offers Play only for the ready version. `RT` requests that version via `ART`; `ART` rechecks the owner, version, state and approved content type against `DB` and reads `STORE`. The runtime interprets the same validated specification version that passed the gate. It reports an explicit ending when the goal predicate is reached.
5. Invalid input fails before queueing. Model outage may receive a bounded retry; permanent schema/reference/unsafe/unsupported-mechanic failures do not repeatedly call the model. Repair is bounded and reruns validation. Exhausted retry, timeout or unverified ending becomes `failed` with a stable class and safe user message; diagnostic details remain correlated in `DB`. A timed-out reachability search is **unverified**, not proof of impossibility. No failed or unfinished version receives a playable URL.

Statuses are `queued → generating → validating → ready`, or `failed` from an unfinished state. A repeated deliberate request creates a new immutable version; a retried event for the same generation ID cannot create another artifact or regress a terminal state. The queue handoff, duplicate delivery, worker loss and publication failure paths require fault-injection tests under PLAT-F04–F09 and GEN-F06–F09.

## Contract and trust boundary checks

- The candidate specification has a version, title/premise/genre intent, goal, bounded scenes/entities/actions, preconditions/effects, starting state, ending predicates, simplifications, controls and instructions. Platform account/project/job metadata is separate. Exact JSON Schema, numeric limits, asset catalogue, state language and event fields remain to be frozen by all three module owners.
- The visible game family is a top-down 2D scene with movement and bounded inspect/collect/interact/choice actions. A request for platformer/racing/card mechanics may be simplified only if the original mechanic, actual replacement and reason are disclosed and the central premise, indispensable actions and goal survive the agreed human fidelity review; preserving the goal alone is insufficient. Otherwise generation fails. The claimed eventual result is a complete playable game within this bounded family; no such result has been demonstrated yet.
- Ending analysis uses bounded discrete logical locations, inventory/flags and deterministic action effects, as proposed in the technology comparison. Retain the winning action trace and replay it in the browser; continuous animation/collision must preserve those logical transitions. A finite-state path is not a proof about unrestricted physics or narrative fidelity.
- The trust transitions are `UI → API` (authenticate and bound input), `MODEL → AI` (treat output as untrusted), `AI → GATE` (independent strict validation), and `STORE → ART → RT` (authorize ready version and deliver approved data). Unknown schema majors, unsafe asset URLs, executable scripts and unsupported actions are rejected before publication. Story text, titles and messages are rendered as text.
- Controlled delivery must reject path traversal, unknown or foreign artifact IDs, unsupported file types and non-ready versions. Exact origin/sandbox policy is a later design review if generated pages or code are ever introduced; the first slice has no generated JavaScript execution.

## Planned integration checkpoints

| Checkpoint | Evidence required before implementation can claim it works |
| --- | --- |
| API/worker contract | A manually authored valid specification and one invalid candidate flow through versioned result messages; the runtime launches the valid version and the invalid one is withheld. |
| Status and recovery | Broker unavailable, worker crash, duplicate result, exhausted retry and artifact write failure leave a visible, recoverable or terminal state, never false `ready`. |
| Browser delivery | An authorized ready version loads; a foreign user, unknown ID, wrong MIME/type and path traversal are denied; no model-generated script runs. |
| End-to-end | Story submission returns IDs; polling progresses; ready reveals simplifications and a playable version; a supported action reaches a visible ending. Record actual evidence once code exists. |

The [system context diagram](../diagrams/system-context.mmd) places the browser client, platform service, generation service and managed infrastructure inside the overall product boundary, with the author and optional model provider outside. The [component diagram](../diagrams/component.mmd) expands those units: `UI` and `RT` form the browser client; `API`, `JOB`, `GATE` and `ART` form the platform service; `AI` is the worker; `DB`, `MQ` and `STORE` are managed infrastructure. The browser, platform and worker boxes mark distinct trust zones within the product. The context arrow labelled “Worker-checked candidate or failure” does not authorize publication: `GATE` validates independently. Approved gameplay state changes occur in the trusted browser runtime. The [use cases](use-cases.md) and [static prototype](../prototype/README.md) describe the corresponding author journey. Authentication, message contracts, storage policy, limits and browser origin controls remain provisional.
