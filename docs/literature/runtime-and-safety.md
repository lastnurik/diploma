# Runtime Architecture Validation and Safe Execution

**Task 08 — Zhaksylyk Aldiyar.** This section reviews research relevant to turning a game specification into executable mechanics, checking whether generated games can end, and containing untrusted output in a browser. It informs design choices; it does not claim that our platform or tests already exist. Five distinct scientific publications from 2021–2025 are used below. The browser documentation at the end is an implementation reference, not counted as a scientific publication.

| Publication | Approach and evidence | Finding and limitation | Consequence for this project |
| --- | --- | --- | --- |
| **Martens, C., Card, A., Crain, H., & Khatri, A. (2024).** “Modeling Game Mechanics With Ceptre.” *IEEE Transactions on Games, 16*(2), 431–444. DOI: [10.1109/TG.2023.3292982](https://doi.org/10.1109/TG.2023.3292982). [Author PDF](https://www.convivial.tools/PapersPublic/ceptre-tog.pdf). | Defines game mechanics as typed, implementation-independent state-transition rules based on multiset rewriting. The authors demonstrate interactive executions, random simulated playthroughs, causal traces and formal queries. | A formal rule representation makes consequences of mechanics inspectable independently of rendering. Ceptre is a research language and toolset; the paper does not show that arbitrary story prompts can be converted correctly into complete browser games. | **Design inference:** put a typed game specification between the language model and a controlled runtime. Model actions with preconditions/effects and explicit win/loss predicates; check that every rule refers to declared entities and that a winning state is reachable under the supported mechanics. We need not adopt Ceptre itself. |
| **Facey, K., Li, C., Martens, C., & Cooper, S. (2025).** “Game Behaviour Trees Using Tile Rewrite Rules.” *Proceedings of the AAAI Conference on Artificial Intelligence and Interactive Digital Entertainment, 21*(1), 216–226. DOI: [10.1609/aiide.v21i1.36825](https://doi.org/10.1609/aiide.v21i1.36825). [Paper](https://ojs.aaai.org/index.php/AIIDE/article/download/36825/38963/40902). | Implements a browser authoring and execution tool using a common game behaviour tree with tile rewrite rules, including explicit `win`, `lose` and `draw` controls. The authors reproduce several 2D games and conduct a formative user study. | A bounded representation can express a range of 2D tile- and turn-based games with reusable patterns. Scope is limited to that model: author-created case studies and seven study participants for a short session cannot establish general coverage or ease of use for platformers, racing, or story-to-game generation. | **Design inference:** constrain the first executable game family and define an explicit end state in the runtime contract. Treat requests outside its mechanics as simplification or failure, not as silently supported genres. A stable runtime can consume declarative rules instead of executing arbitrary generated scripts. |
| **Villanueva Aylagas, M., Bergdahl, J., Gillberg, J., Sestini, A., Tolstoy, T., & Gisslén, L. (2024).** “Improving Conditional Level Generation using Automated Validation in Match-3 Games.” *IEEE Transactions on Games*. DOI: [10.1109/TG.2024.3440214](https://doi.org/10.1109/TG.2024.3440214). [Author manuscript](https://media.contentapi.ea.com/content/dam/ea/seed/presentations/seed-tog-conditional-level-generation-paper.pdf). | Avalon uses gameplay statistics from bot playthroughs to condition a level generator and compares it with an ablated model without difficulty conditioning. The reported model creates more valid match-3 levels than that ablation. | Generating a syntactically shaped level does not ensure solvability; playability feedback matters. The experiment concerns a simplified match-3 layout generator and learned model, not unrestricted narratives or a cross-genre browser platform. | **Design inference:** validate completion separately from JSON/schema validity. For each supported mechanic, run a bounded simulated playthrough or reachability check and record failures. Include a prewritten valid game as a baseline for launch and completion checks. We cannot import the paper’s measured improvement as our own success rate. |
| **Fernandez-de-Retana, A., Rautenstrauch, J., Santos-Grueiro, I., & Stock, B. (2025).** “A Permissions Odyssey: A Systematic Study of Browser Permissions on Modern Websites.” *Proceedings of the 25th ACM Internet Measurement Conference*, 342–358. DOI: [10.1145/3730567.3764489](https://doi.org/10.1145/3730567.3764489). [Author page](https://jannisbush.github.io/publication/2025-imc-permissions/). | Measures browser permission policy and iframe delegation across the top one million websites. It reports frequent overly broad delegations and provides tools for setting least-privilege permission policies. | Browser embedding can grant capabilities unnecessarily. This is an observational study of popular sites, not a direct penetration test of generated games or proof that a given sandbox configuration is secure. | **Design inference:** if game output is loaded in an iframe or separate origin, grant only required browser capabilities. Do not hand generated content the parent application’s authentication context or unrestricted navigation. Check the actual response headers and iframe configuration in browser tests. |
| **Hilbig, A., Lehmann, D., & Pradel, M. (2021).** “An Empirical Study of Real-World WebAssembly Binaries: Security, Languages, Use Cases.” *Proceedings of The Web Conference 2021*, 13 pp. DOI: [10.1145/3442381.3450138](https://doi.org/10.1145/3442381.3450138). [Author PDF](https://software-lab.org/publications/www2021.pdf). | Collects 8,461 unique WebAssembly binaries from repositories, packages and websites, then applies static and manual analyses. It finds a diverse ecosystem, including memory-unsafe origins and imported host APIs with security implications. | A low-level browser execution format is not a blanket guarantee of safe generated code. The sample is a 2021 snapshot of existing binaries and does not benchmark this project’s prospective runtime or compare JavaScript and WebAssembly for our workload. | **Design inference:** do not treat “compile generated code to WebAssembly” as the security plan. Prefer validated data and a trusted game engine for the first version. If future work permits generated binaries or scripts, review their imports/capabilities and isolate them separately. |

## Synthesis for the architecture and evaluation plan

The research supports a **proposed** pipeline of story → constrained, versioned game specification → structural and semantic validation → controlled 2D runtime → bounded playthrough/ending check → published game or explicit failure. Ceptre and the tile rewrite work motivate a formal, limited mechanic vocabulary; Avalon motivates gameplay validation beyond parsing. The security papers motivate a separate trust boundary around any rendered output and explicit capability restrictions. None of these papers demonstrates our proposed pipeline end to end, so that remains an engineering hypothesis to test.

For a first version, define a small supported set of mechanics, immutable specification schema, input limits, allowed assets and win/lose conditions. Reject unknown operations, references to missing objects, and invalid transitions before publication. Test that the browser can start the game and the supported actions can reach an end state. A search or solver result should be bounded in time and state count; a timeout is “not verified,” not proof of impossibility. Store validation and runtime errors against the project version. If the project later supports arbitrary generated HTML/JavaScript, it needs a separate origin, restrictive sandbox/permission policy, navigation controls, resource limits and security review. This is a design proposal, not an implementation claim.

**Operational browser reference (not part of the scientific count):** MDN’s [`<iframe>` documentation](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) warns that combining `allow-scripts` and `allow-same-origin` on same-origin content can defeat the sandbox, and that content opened outside the sandbox should be served from a separate origin. The final configuration must be checked against current browser behavior and the actual execution model.
