# Requirements Specification

**Status, October 2026:** Initial requirements for the planned product and first bounded playable slice. They are not implemented or empirically validated. The [proposal](proposal.md) establishes the aim, the [scope and game contract](decisions/scope-and-contract.md) describes proposed constraints, and the [frontend](requirements/frontend.md), [platform](requirements/platform.md) and [generation](requirements/generation.md) files contain module-level acceptance checks.

**Priority:** Must means needed for the first integrated request-to-playable-game slice; Should means a later enhancement. **Evidence provenance:** P = supervisor proposal via `proposal.md`; C = proposed scope contract; L = literature implications. The supplied questionnaire records have unresolved respondent provenance, so no requirement is represented as confirmed by user evidence.

**First-slice reading guide:** An author submits a story, receives traceable progress, reviews any simplification, and plays an approved version to an ending. The platform must keep versions and failures visible; the generator must stay within supported mechanics; the runtime must use validated data. The tables below state observable acceptance for each requirement. Module files linked above hold implementation-level detail.

## Functional requirements and acceptance

| ID | Priority · source | Requirement | Observable acceptance and detailed IDs |
| --- | --- | --- | --- |
| R-01 | Must · P,C | Author creates or edits a story request and states genre intent, goal and main action. | Given valid input, story and parameters are preserved together; empty/invalid fields show a correction. `FE-01–02`, `PLAT-F01`, `GEN-F01`. |
| R-02 | Must · P,C | A submission creates a traceable project version and an asynchronous generation job. | API returns stable project/version/generation IDs and `queued` without waiting for model output; explicit retry does not duplicate one job. `FE-03`, `PLAT-F02–04`. |
| R-03 | Must · P,C | Client shows actual generation state and safe failures. | Reload reads the current `queued`, `generating`, `validating`, `ready` or `failed` state; failed/unvalidated output has no Play action or game URL. `FE-04`, `PLAT-F05`, `PLAT-F11–12`. |
| R-04 | Must · P,C,L | AI extracts genre intent, central objective and requested actions, then maps them to a bounded supported mechanic set. | Structured intent/action record exists for each evaluation prompt or returns a reasoned failure; reviewer compares intent to original story. All emitted action kinds belong to the approved set. `GEN-F01–02`. |
| R-05 | Must · P,C | AI produces an immutable, versioned game specification with scenes, entities, rules, controls and ending. | Strict validator resolves starting scene, references, state effects and at least one winning predicate; unknown major schema/operations fail. `GEN-F03–04`, `PLAT-F07–08`. |
| R-06 | Must · P,C,L | Unsupported mechanics are simplified explicitly only when the central story remains recognizable. | Result lists original request, replacement and reason; human rubric checks premise/goal; unacceptable substitution yields `failed`. UI displays the list. `GEN-F02`, `FE-05`. |
| R-07 | Must · P,C | Generation validates schema, references, action semantics and safe content; recoverable errors receive bounded repair. | Invalid fixtures fail with codes; repair attempts stay within configured bounds and rerun checks; unrepairable result never publishes. `GEN-F06–08`, `PLAT-F07`, `PLAT-F09`. |
| R-08 | Must · P,C | A ready game has a reachable ending in the supported state model. | Finite state exploration identifies a path from initial to winning state and a browser walkthrough observes the ending; timeout is `unverified` and cannot be published as ready. `GEN-F05`, `PLAT-F09`, `FE-07`. |
| R-09 | Must · P,C | Browser runtime loads the exact validated version and supports its declared controls/actions. | Validated generated game starts, action changes state and ending appears; invalid/missing artifact shows controlled error. `FE-06–07`, `PLAT-F08–11`. |
| R-10 | Must · P,C | Author sees a catalogue of projects, versions, failures and earlier ready results. | Creating a new attempt preserves prior version input, result and status; opening earlier ready version loads that version. `FE-08`, `PLAT-F01–02`. |
| R-11 | Must · P,C,L | Author can revise a request and deliberately retry after failure or regenerate after success. | A new version/job is linked to its predecessor; retained story can be edited and the old result is unchanged. This can use the ordinary generation endpoint; a separate convenience retry operation is optional. `FE-09`, `PLAT-F02–03`; `PLAT-F15` specifies the optional convenience operation. |
| R-12 | Must · P,C | Platform records useful errors and history across the asynchronous boundary. | A generation ID traces submission, worker result, validation and terminal status; broker outage, duplicate delivery and provider error are handled without silent stuck or double published versions. `PLAT-F04–06`, `PLAT-F12–13`, `GEN-F08–09`. |
| R-13 | Should · P,L | Interface explains supported actions and gives useful next steps when generation is uncertain. | Prototype/user walkthrough identifies available controls, simplification location and failure recovery without claiming unsupported genre mechanics. `FE-10–11`. |

## Non-functional requirements and acceptance

| ID | Priority · source | Requirement | Observable acceptance and detailed IDs |
| --- | --- | --- | --- |
| Q-01 | Must · P,C | Generated/model text is untrusted data; only validated data and approved assets reach a fixed runtime. | Reject unknown operations, unsafe asset URLs and unapproved artifact IDs; test path traversal, cross-user access, content type and no model-generated executable script. `GEN-N01`, `PLAT-F10`, `FE-N04`. |
| Q-02 | Must · P,C | Jobs, game data and publication are version consistent and recoverable. | Duplicate event leaves one terminal outcome; older versions stay immutable; invalid result is not marked ready. `PLAT-F02`, `PLAT-F05–09`. |
| Q-03 | Must · P,C | Inputs, output size, retries and checks have documented bounds. | Boundary and timeout fixtures terminate with stable error/status; exact numbers are set before implementation and tested. `PLAT-F14`, `GEN-N03`. |
| Q-04 | Must · P,L | Authoring screens work at proposed 375, 768 and 1280 px widths and through keyboard navigation. | Manual viewport/keyboard checks find no clipped essential controls; focus, text errors and status states are perceptible. `FE-N01–02`; proposed fixtures, not a claim of full WCAG certification. |
| Q-05 | Should · L | Dynamic status and error changes are understandable to assistive technology. | Keyboard and one screen reader/browser walkthrough observes announcements and predictable focus. `FE-N03`, `FE-N05`. |
| Q-06 | Must · P,C | A team member can reproduce local services and integration tests when code exists. | A clean setup following README and example configuration starts required services; tests cover success, broker failure, duplicate job, invalid game and safe delivery. `PLAT-N01`. |
| Q-07 | Must · P,C | Generation results and evaluation are traceable without committing confidential stories or credentials. | Store prompt ID, schema/model config, validation outcome and artifact hash; tests replay a saved spec deterministically; Git inspection finds no secrets/raw contacts. `GEN-N02`, `PLAT-F13`. |
| Q-08 | Must · P,L | Quality is reported with distinct denominators for validity, launch, main actions, ending and simplification fidelity. | Fixed corpus, conditions, manual baseline and rubric are documented; failures counted rather than excluded. No success percentage is asserted before measurement. `GEN-N04`. |

## Alignment and open decisions

The planned author flow is **story/parameters → project version/job → intent and game data → validation/repair → ready artifact plus simplifications or visible failure → browser play and ending**. The context, use case and component diagrams must show these same states and module boundaries. The [project plan](project-plan.md) sets out the checks and later evaluation for these outcomes.

Before implementation, the team must approve an exact schema and limits, server/runtime selection, authentication/access policy, artifact origin controls, error catalogue and win-condition checker. `PLAT-F01` currently assumes a signed-in owner to protect project data; authentication design is a team decision, not an established fact from the proposal. The first slice's core regeneration path in R-11 is mandatory; `PLAT-F15` currently labels a dedicated retry action as Should, which is consistent only if the ordinary generation endpoint supports that core path. Confirm this API interpretation with the three module owners. User research and supervisor review may change priorities, and such decisions must be recorded with resulting edits rather than retroactively presented as original requirements.
