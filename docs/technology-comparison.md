# Technology Alternatives for the First Version

**Decision status:** proposed for team and supervisor review on 22 October 2026. This comparison covers three key decisions, each with three reasonable alternatives. The first implementation target is a bounded top-down 2D scene game with move, inspect, collect, interact and choice actions, a visible simplification list and a reachable ending. The options below are assessed against that target and the three owners' proposed module boundaries. No option has yet been benchmarked or implemented for this diploma project. Official documentation was checked on **22 October 2026**; capability statements below describe documented features, while effort and suitability judgments are project inferences. Candidate version families are not claims about the latest release; pin exact dependencies before implementation.

| Decision | Provisional recommendation | Main reason | Proof required before locking it |
| --- | --- | --- | --- |
| Server platform and asynchronous work | Spring Boot API, PostgreSQL, RabbitMQ, separate Python generation worker | Fit with the backend and AI owners' experience and a clear job contract | Queue/recovery integration spike and reproducible Compose deployment |
| AI generation and validation | Versioned structured game specification interpreted by a fixed runtime | Observable rules, bounded supported mechanics and deterministic checks | Manually authored specification runs; validator catches invalid and unreachable cases |
| Browser game runtime | Phaser 3, with a fixed adapter for validated game data | Browser-native scenes, input and 2D facilities suit the proposed slice | Load a handwritten specification, play to an ending, reject an invalid one |

## Product criteria used across the decisions

The nontechnical author should be able to submit a story, understand any simplification, receive a clear success or failure state, and play the main action through to an ending. In that order, the priorities are **intent preservation and a complete bounded game**, **observable validation and recoverable failure**, then **delivery effort within the three-person project**. Raw request throughput, model popularity and a runtime's feature count do not decide this first version. The authoring interface remains a separate web UI: none of the game-runtime alternatives supplies the story form, job progress or correction flow automatically.

The three decisions are linked: a fixed runtime requires a supported data contract; that contract defines what the generator and validator can promise; the job platform must preserve the resulting validation status. PostgreSQL is held constant here as the proposed durable record store, so this comparison does not claim to have selected it over other databases.

## 1 Server platform and job execution

The server must expose project/version APIs, persist status, hand long-running generation to a worker, survive retries without duplicate publication, and serve only validated artifacts. The platform owner is assigned backend/architecture; the generation owner is assigned a Python AI service. The following assessment uses **the same criteria for every alternative**.

| Alternative | API and component boundary | Jobs and failure handling | Artifact safety and data | Delivery effort and team fit |
| --- | --- | --- | --- | --- |
| **A Spring Boot + PostgreSQL + RabbitMQ + Python worker** | Java API owns projects/versions/status; Python worker receives a versioned message contract. Spring Boot documents AMQP integration. [S1] | RabbitMQ acknowledgements/redelivery require idempotent generation IDs. Configure bounded retries, dead-letter handling, timeouts and recovery for failed publication; broker alone does not make a transaction atomic. [S1–S2] | Database is canonical for job/version records; publish the game artifact only after validation. | Fits Aldiyar's Java/Spring experience and Nurgeldi's Python work, but runs more services and needs tested cross-language messages. |
| **B FastAPI + PostgreSQL + Celery/Redis workers** | Python across API and worker can share types; ownership boundaries still need explicit interfaces. | Celery provides worker tasks and retry/state machinery; set limits and keep user-visible status in PostgreSQL. FastAPI identifies tools such as Celery as appropriate alternatives for heavy work that need not share the API process. [S3–S4] | Same publication gate and data separation as A; Redis result state is not the authoritative project record. | Fewer language transitions; moves platform implementation away from the assigned backend owner's stronger Java/Spring experience. |
| **C Go/Gin + PostgreSQL + Asynq/Redis + Python AI service** | Gin API enqueues Asynq tasks; a Go worker calls a versioned Python generation service. Asynq is a Go task library, so this option does not assume native Python task consumption. [S5–S6] | Asynq offers task state, retries and deadlines; tune retries for costly model calls and implement idempotent publication. [S6] | Same database/artifact gate; HTTP and queue failures need explicit reconciliation. | Feasible, but introduces Go into the platform role and an additional Go-worker/Python-service boundary. Java/Python/JavaScript in A and Go/Python/JavaScript in C both span three languages; language count alone does not favor A. |

**Recommendation:** A is the best current fit for responsibility and traceability; B is a fallback if cross-language queue integration proves too costly. This is a project-fit inference, not a reliability or speed ranking. An integration spike should prove that a database write followed by queue publication cannot leave an invisible stranded job; that a worker crash causes bounded recovery without publishing twice; and that exhausted retries become a visible `failed` status. Choose an outbox or equivalent durable reconciliation in the contract before implementation; publisher confirms and consumer acknowledgements cover different handoff stages and do not make the database/broker write atomic. [S2] The API should immediately return a generation ID and expose later status/result through a documented contract.

## 2 AI generation and validation method

The AI module must extract genre, goal and key actions from the story, produce coherent scenes/rules/data, preserve intent when simplifying an unsupported mechanic, and either produce a validated playable result or explain failure. The following ratings are qualitative design assessments; model usage and cost have not been measured.

| Alternative | Control and intended actions | Playability validation | Repair, failure and safety | Cost and reproducibility |
| --- | --- | --- | --- | --- |
| **A One-shot complete HTML/JavaScript generation** | Permits mechanics outside a fixed schema, but the model chooses code and may silently omit the defining action. | Browser launch is easy to check; whether actions work and an ending is reachable needs game-specific tests. | Full regeneration can change unrelated behavior; arbitrary generated script needs strict isolation. | Little initial engine work, potentially substantial debugging; no measured API or maintenance cost. |
| **B Staged code generation with execution feedback** | Separates state, rules and rendering, then revises code after failed checks. Behavioral intent still depends on tests. | Execution feedback catches code errors, but smoke tests may miss wrong rules or win conditions. | Bounded repair and sandboxed execution are necessary; each revision may create regressions. | A staged/repair policy can require additional calls and orchestration; cap its call budget. Logs aid diagnosis, but storing outputs is still necessary for replay. |
| **C Structured, versioned game specification plus fixed runtime** | The schema represents goals, supported actions, state transitions and disclosed simplifications. Freedom is limited to the allowed mechanic set. | Validate types/references/rules and a finite-state winning path, then run browser-level action and ending tests; narrative fidelity still needs human review. | Repair invalid data within a fixed limit, or return a specific failure. The browser interprets validated data rather than executing model-generated JavaScript. | Upfront schema/runtime work; stored input, schema/model version and output aid diagnosis. Lower future cost is a hypothesis, not a measured result. |

**Recommendation:** C matches the proposal's emphasis on a complete and explainable game. Parse a strict schema, check references and state transitions, find and retain a winning action trace for supported finite mechanics, perform browser checks, and attempt a bounded repair for specific errors. A timeout during reachability search means **unverified**, not proven impossible. If a requested mechanic cannot be mapped without losing the main premise, return a failure rather than relabeling a different game. A finite-state result applies only to the modeled rules: define discrete logical locations, bounded inventory/flags and deterministic action effects for the first slice. If movement is animated continuously, the adapter must preserve those logical transitions; replay the witness trace in the browser to catch collision or mapping differences. Avoid claiming a proof about unrestricted physics. Staged code generation remains a research alternative if later requirements cannot fit the contract and the team can validate its added execution risks. Research on generated games supports checking semantic effects and endings separately from compilation or launch; it does not establish a success rate for our browser platform. [A1–A5]

## 3 Browser game client and runtime

The runtime must read approved game data, display a bounded 2D scene, support the first action set, expose progress/ending events and embed in the browser authoring client. Every alternative still requires **our own specification adapter, goal rules and input validation**.

| Alternative | 2D and input features | Specification loading and ending | Browser integration and safety | First-version effort |
| --- | --- | --- | --- | --- |
| **A Phaser 3.90.0 candidate** | Scenes, keyboard/pointer input, animations and built-in physics systems are documented. [R1] | Load JSON/assets, then map validated data to fixed scenes/rules; write our own win/restart logic. [R1] | JavaScript runtime embeds directly in the web app. Treat text/assets as untrusted; do not evaluate generated code. | Best fit for a small game engine prototype, subject to a proof of concept. |
| **B PixiJS 8** | Rendering, scene graph and pointer events; its own docs call it a rendering engine, so gameplay rules/collision flow are ours or added separately. [R2] | Load data/assets, build custom rules, inputs and ending checks. | Browser embedding is straightforward; the same input/content protections apply. | More gameplay infrastructure for the team; useful if a mostly visual narrative needs a highly custom renderer. |
| **C Godot 4 web export** | Full 2D editor, scene and physics facilities. [R3] | A prebuilt exported game can read runtime data, but the team must author its loader and mapping; exports are packaged projects. | Web export needs browser WebAssembly/WebGL 2.0. Threaded builds require cross-origin isolation; single-thread exports are supported. Godot 4 C# projects cannot currently export to web, so this option assumes GDScript or another supported route. [R3] | More web packaging/data handoff work for this version; attractive if future authored mechanics become more complex. |

**Recommendation:** A fits the proposed top-down browser slice without requiring the team to assemble a game engine from rendering primitives. The proof of concept must load a **handwritten** valid specification, move a player, inspect/interact, collect, reach a declared goal, show an ending and reject an invalid specification. Test target browsers and record artifact size/load time; do not claim unmeasured speed or size benefits. Use PixiJS if the slice becomes primarily custom visual narrative and the team accepts implementing gameplay infrastructure. Revisit Godot if editor-authored mechanics justify the export/hosting boundary. No runtime choice by itself guarantees that a generated game is completable.

## Cross-component contract and next decision gate

The server owns the project/version/job record and publishes only validated artifacts. For the recommended data-driven approach, the AI worker returns a versioned game specification, simplification list, validation findings and either a candidate data reference or a failure code. A published game consists of approved data/assets plus a pinned trusted runtime; generating or rebuilding executable code per story is not required by this decision. The browser runtime accepts only the supported schema version and approved assets. Both validator and runtime must interpret the **same immutable version** of the specification; record the schema, validator and runtime versions with its content identifier. Preserve the last validated version if a later generation fails, and map unknown schema versions to a visible error. The exact schema, message fields, size limits, asset catalogue and deployment boundaries still require a joint M/A/N design decision; the individual recommendations above are not a claim that the stack has been installed or approved.

Before implementation, agree the contract and run the two small proof-of-concept checks above. If RabbitMQ handoff or Phaser data loading fails the acceptance conditions, revisit the relevant comparison and record the revised decision. Scope remains the bounded top-down 2D game; platformer, real-time racing and deck-building remain evaluation/stretch cases rather than supported mechanics.
