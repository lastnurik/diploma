# Platform Requirements

**Task 18 — Zhaksylyk Aldiyar. Status: proposed for team and supervisor review.** These requirements describe the eventual first executable slice; they are not claims of implementation by the 24 October pre-defense. They derive from the [project proposal](../proposal.md) (**P**) and the [first-version scope and game contract](../decisions/scope-and-contract.md) (**C**). **Must** means required for that slice; **Should** means planned if it does not delay a working request-to-game path. Endpoint names and numeric limits remain draft decisions, but each acceptance test is observable.

| ID · priority | Requirement and source | Verifiable acceptance criterion |
| --- | --- | --- |
| **PLAT-F01 · Must** | Create, read and list a project owned by the signed-in user; retain the original story and selected parameters. **P objectives 1, 5; C actors 1–2.** | Given an authenticated user and valid bounded input, create returns a stable project ID and saved fields; list/read return that user's project. A second user cannot read or change it; unauthenticated access is rejected. |
| **PLAT-F02 · Must** | Create a distinct project version for each generation attempt, preserving previous versions and their input/specification/artifact references. **P objective 5; C proposed versioned specification and job states.** | Two attempts for one project have different version IDs; the first remains readable after the second starts or fails. Editing a later request does not mutate the prior version's stored story or validated specification. |
| **PLAT-F03 · Must** | Accept a generation request asynchronously and return its stable generation ID and initial state without waiting for model execution. **P objective 5; C job states.** | A valid request returns a generation ID and `queued` status before worker completion. Repeated submission creates a new version unless the same explicit idempotency key is retried; invalid input returns a client error without a queued job. |
| **PLAT-F04 · Must** | Hand off the generation request to a worker using a versioned contract; recover from a failed publication handoff. **P objective 5; C actors 2–3; technology comparison task 13.** | A worker receives the expected IDs, schema version and input reference. If queue publication fails, the job remains traceably pending/retryable or becomes visibly failed; it cannot remain indefinitely `queued` with no recoverable work. Verify with a broker unavailable test. |
| **PLAT-F05 · Must** | Persist allowed status transitions `queued → generating → validating → ready`, or to `failed` from an unfinished state, with timestamps and safe progress text. **C job states.** | Status polling returns the correct generation/version IDs, state, timestamps and public message; invalid transitions are rejected; terminal `ready` or `failed` does not regress on duplicate events. |
| **PLAT-F06 · Must** | Bound worker retries and execution time, classify transient service failures separately from invalid or unsafe game output, and make processing idempotent. **P objective 3; C failure classes; task 13.** | Simulated transient failure retries no more than the configured bound; permanent validation failure does not cause repeated model calls. Redelivering the same generation event leaves exactly one ready artifact/version and one terminal state. Timeout is recorded as unverified/failed, not as proof the game is impossible. |
| **PLAT-F07 · Must** | Receive the AI component's result through an agreed versioned message contract and validate its identity and schema before saving or publishing it. **P individual roles and objective 5; C specification.** | Result with matching generation ID and supported `schemaVersion` is accepted for further validation; unknown schema major, mismatched project/version, missing fields or unknown action kind is rejected with a recorded error. The platform cannot mark it `ready` merely because the worker reported success. |
| **PLAT-F08 · Must** | Store generated specification, game data, simplifications and artifact metadata per immutable project version, separated from platform account metadata. **P objectives 2, 4–5; C specification.** | Retrieved version yields the exact validated specification used by the runtime and its simplification list; earlier versions are unchanged. The stored artifact reference resolves only to the version that owns it. |
| **PLAT-F09 · Must** | Publish a version only after schema/reference validation, safety checks and the agreed launch/completion verification have passed. **P objectives 3–5; C completion.** | An invalid, unsafe or unverified game has no public playable URL and is not returned as `ready`. A passing validated version has a resolvable artifact reference; its status, validation outcome and artifact refer to the same version. A bounded reachability timeout is reported as unverified. |
| **PLAT-F10 · Must** | Deliver only approved game assets/data and the trusted browser runtime through controlled routes. The first slice never executes model-generated JavaScript. **P safe delivery responsibility; C trust boundary.** | Requests with `../`, unknown artifact IDs, foreign-user IDs, unsupported file types or unapproved versions cannot obtain a playable artifact. Responses set the approved content type and `X-Content-Type-Options: nosniff`; inspection finds no model-supplied executable script in the allowed game data. If embedding generated pages is introduced later, it requires a separately tested sandbox/origin policy. |
| **PLAT-F11 · Must** | Expose project/version, generation-status, simplification and playable-result reads for the frontend. **P objective 1; C actors and job states.** | For a ready version, the client can retrieve status, simplifications, instructions/controls and game URL/data using stable IDs. For queued/failed versions, the API supplies status and a safe message without exposing an unvalidated URL. |
| **PLAT-F12 · Must** | Return structured user-facing errors while recording diagnostic details against the generation ID. **P objective 3 and Aldiyar role; C failure classes.** | Invalid request, unavailable model, bad schema, unsupported mechanics, missing references, failed verification, runtime build failure and unsafe output map to documented error codes; the public response gives an actionable reason without raw model output, stack traces, secrets or another user's story. |
| **PLAT-F13 · Must** | Record audit events for generation creation, state changes, validation, publication and failure, with request/generation correlation. **P Aldiyar role; C job states.** | An integration test can trace a generation ID from request through terminal outcome and identify error class and timestamps. Logs avoid API keys, full story text, personal data and raw generated content. |
| **PLAT-F14 · Must** | Limit request size, allowed parameter values, model result size and artifact count/size according to documented configuration. **C bounded schema and untrusted output; P safe content.** | Oversized input/result or unsupported parameter is rejected before publication with a documented error; a valid boundary-size sample is accepted. Exact numerical limits are set and tested before implementation release. |
| **PLAT-F15 · Should** | Offer a controlled retry/regeneration action that creates a new version and preserves the failed attempt for inspection. **P frontend journey and version model; C job states.** | A failed version remains readable with failure code, while retry creates a new generation and version IDs. The UI can link the two attempts; it cannot overwrite the old artifact. |
| **PLAT-N01 · Must** | Provide reproducible local deployment and integration tests for API, database, broker/worker boundary and artifact delivery. **P Aldiyar independent output and project stages.** | A documented clean setup starts required services with example configuration; tests cover valid request, broker failure, duplicate event, invalid spec, ready publication, cross-user denial and safe artifact access. Actual commands and results are recorded once code exists. |

## Draft API contract for review

This is a proposed endpoint shape, not a claim that routes exist. The team must align it with frontend mockups and the AI message schema before implementation.

| Operation | Input → output | Error/visibility rule |
| --- | --- | --- |
| `POST /projects` | Bounded story/title/parameters → project ID | `400` validation error; `401` unauthenticated. |
| `GET /projects`, `GET /projects/{id}` | Authenticated list or project with versions | `403`/`404` for unavailable project; never list another user's items. |
| `POST /projects/{id}/generations` | Project ID, parameters and optional idempotency key → generation/version IDs and `queued` status | `400` bad input; `403` foreign project; transient enqueue failure is visible/recoverable, not falsely `ready`. |
| `GET /generations/{id}` | Generation ID → state, timestamps, public message, error code or ready artifact ID | No raw diagnostic log or unvalidated game URL; unknown/foreign ID denied. |
| `GET /projects/{id}/versions/{versionId}` | Version ID → preserved metadata, simplified mechanics, ready artifact reference if published | Failed/unfinished version remains traceable but cannot be launched. |
| `GET /artifacts/{id}/game` | Approved artifact ID → trusted runtime and validated game data | Deny unknown, foreign, non-ready and unsafe artifacts; enforce the selected browser delivery policy. |

**Open alignment decisions:** exact authentication method; resource limits; whether the project is created separately from its first generation; detailed error-code catalogue; event schema and result publication path; broker recovery strategy; artifact storage implementation and browser headers. These decisions belong in the shared contract/architecture and technology review, with requirements and tests revised together. No invented values are treated as approved targets.
