# Verification Plan for the First Executable Slice

**Status, October 2026:** Planned evaluation, with no executed cases. The checks assess the proposed [requirements](requirements.md) and [scope contract](decisions/scope-and-contract.md) using the [story prompt set](../tests/evaluation-prompts.md). A `ready` label requires independent verification.

## Strategy and execution record

Verification proceeds from the versioned game contract outward: strict specification checks; state-space ending check; generation and queue integration; authenticated artifact delivery; then browser interaction and a human story-fidelity review. A manually authored valid game is the first runtime fixture. Calibration prompts C01–C04 help develop the validator and flow; evaluation prompts E01–E08 remain fixed for later scoring. The generated result is untrusted data, and the browser uses the same immutable version that passed validation. A failed or unverified result cannot acquire a playable URL. Each retry is a new linked version except idempotent redelivery of the same accepted request.

Before execution, agree and record the schema version, allowed action and asset lists, input/output/state limits, repair/search/queue timeouts, error codes, authentication policy, browser versions, provider/model configuration and runtime commit. Use a controllable provider stub and queue fault injection for deterministic failure cases; use the real configured provider only for the separately recorded corpus run. Create fixtures from the approved schema rather than assuming the illustrative field names in the scope contract are already final. Never store credentials or private stories in test artifacts.

For each run retain: case ID, date, tester, commit, fixture or corpus ID and hash, schema/runtime/model configuration, project/version/job IDs as applicable, actual state transitions, assertion results, redacted logs, artifact hash, and screenshots or a short browser recording for visible outcomes. Mark each case **pass, fail, blocked, or not run**, with a defect link and rerun record. A manual review records the reviewers and their reasoning; it does not turn an automated check into a measured result.

## Corpus use and human checks

The V02/V14 fixture establishes that the trusted runtime and checks can handle a known correct game independently of the generator. Once the integration path works, run C01–C04 for calibration and freeze E01–E08, their Git commit and prompt hashes before evaluation. For each E case record validity, launch, central-action fidelity, reachable and observed ending, simplification disclosure, failure class, attempts, latency and cost separately. E01 must return the dog to safety; E02 requires the fuse before restart; E03 needs both routes; E04 needs a coherent clue/code chain. E05/E06 need explicit simplification and human judgment; E07/E08 are expected transparent rejections under the proposed scope. A truthful rejection is not a playable success. Two reviewers independently annotate premise, indispensable actions, goal and acceptable simplification before seeing outputs, then record disagreements and adjudication. These are future checks, not observed outcomes.

## Metrics and baseline

**Proposed protocol, not results.** This evaluates R-04–R-09 and Q-08 in [requirements.md](requirements.md): a game must preserve meaningful story actions and reach an explicit ending, not merely launch. Review and freeze this protocol before the scored run; changes create a new version and a separately reported cohort.

### Fixed sample, conditions and attempts

Use the exact E01–E08 story strings from [corpus v0.1](../tests/evaluation-prompts.md), **three independent generation trials per prompt: 24 scheduled trials**. C01–C04 are calibration only. Preserve the corpus commit/hashes and pre-output human annotations. Report E01–E04 (12 trials, in scope), E05 (3, conditional platformer simplification), E06 (3, stretch racing request with conditional replacement allowed by its reference), and E07–E08 (6, expected scope rejection) separately. E06 remains a stretch case even if a replacement passes review; it is not evidence of native racing support.

Freeze the application/runtime/schema commits, allowed mechanics/assets, provider/model version, system prompt, temperature/seed policy, default user parameters, resource limits, hardware, queue concurrency and browser/OS versions in a run manifest. Use the same configuration and one active trial at a time; no manual prompt edits or cherry-picked outputs. Record seeds when supported and acknowledge provider nondeterminism. Proposed evaluation bounds are **180 seconds per generation trial including queueing/repair, at most two repair calls after the initial call, 10 seconds or 100,000 explored states for ending analysis (whichever first), 30 seconds for browser launch and five minutes for a browser walkthrough**. These are initial experimental limits, not measured performance guarantees; align them with the agreed contract before freezing. Record actual configured values if review changes them. Evaluate every produced artifact in each declared supported browser; a browser-level pass requires all declared browsers to pass.

A trial is one newly submitted generation job/version; automatic repair calls belong to that trial. The three scheduled trials are independent, not “retry until success.” Broker redelivery is not another trial. Log initial/repair calls and per-call outcomes; retain both first-candidate validity and final-after-repair validity. Deliberate user retries or diagnostic reruns receive linked new IDs and are reported separately, never substituted for failed scheduled trials. Do not tune from scored outputs; any subsequent tuning requires a new evaluation cohort.

### Measures and denominators

Let **N** be initiated scheduled trials in the stated cohort/group, **O** trials returning a final candidate specification (even if invalid), **L** trials passing safe launch, and **D** trials returning a candidate that changes or omits a requested mechanic, as identified against the frozen annotations. Record counts as numerator/denominator and percentage only when the denominator is nonzero; otherwise report **N/A**. Publish initiated/scheduled coverage alongside all results. No complete 24-trial claim is valid while scheduled trials remain not run.

| Measure | Numerator / denominator and pass evidence |
| --- | --- |
| Final specification validity | Final candidates passing schema, references, allowed actions/assets and safety gates **/ N**. Also report **/ O** as a conditional diagnostic; absence of output remains a failure in the primary rate. |
| Safe browser launch | Trials loading the exact validated artifact, showing start/controls and no unsafe execution or fatal startup error within the bound **/ N**. A `ready` label alone is insufficient. |
| Central-action fidelity | Trials in which all indispensable actions (or pre-allowed replacements) visibly cause the required state changes and pass the action rubric below **/ N**; also report **/ L** for launched-output diagnosis. |
| Reachable ending | Trials with a retained valid path from initial state to the declared winning predicate within search bounds **/ N**. Timeout/resource exhaustion is unverified and fails this measure; it is not proof of unreachability. |
| Observed browser ending | Trials whose browser walkthrough performs required actions and displays the correct explicit ending within the bound **/ N**. A solver path without browser evidence does not pass. |
| Simplification fidelity and disclosure | Changed-output trials passing premise, action, goal and disclosure rubric **/ D**. Silent changes belong in D and fail. Rejections and unchanged outputs are N/A for this conditional measure; separately report D/N and fully faithful playable successes/N. |
| Complete playable generation success | Trials passing validity, safe launch, action fidelity, reachable ending, observed ending and the applicable fidelity/disclosure rubric **/ N**. Report overall and by the four groups; never count a transparent rejection as a playable success. |
| Transparent scope rejection | E07–E08 trials returning a specific supported-scope reason within the bound, no playable URL and no false ready result **/ initiated E07–E08 trials**. This is a separate handling measure. Report reasoned E05/E06 rejections separately as acceptable handling, but failed playable generation. |
| Playable-generation failure | Trials not meeting complete playable success **/ N**, including valid scope rejections. Split failure reasons below; pending human review is unverified, not success. |

### Human fidelity rubric and manual baseline

Two team reviewers independently score every candidate using the frozen story annotations, specification, simplification screen and observed play. For each dimension use **2 = preserved/fully demonstrated, 1 = partial or uncertain, 0 = missing/contradicted**: (a) central premise and indispensable roles, (b) every indispensable action and its effects, (c) requested goal and coherent ending, (d) complete, accurate visible disclosure of each changed mechanic and its reason. An explicitly pre-allowed replacement can score 2; naming the original genre alone cannot. Disclosure is N/A only when both reviewers find no change. Pass requires 2 on all applicable dimensions; do not average away a missing core mechanic. Save both initial scores, reasons, screenshots and disagreement count. Resolve disagreement by recorded discussion with the third member adjudicating unresolved cases; retain both originals and the final reason. Rejected/no-output trials receive no candidate score and cannot pass playable success. These are team judgments, not independent end-user validation.

Before scored generation, author **one C01-like specification manually**, document the expected key/door/lamp action path and explicit ending, and run V02/V14 on the same frozen runtime/browser/configuration. Repeat its launch/action/ending walkthrough three times and retain all outcomes. This control isolates runtime/interaction defects from generation defects; it is not a measured competing generator or a basis for superiority claims. If it fails, fix the runtime and freeze a new version before starting the scored cohort. Do not use this authored artifact as a scored generated result or silently replace any E output with it.

### Failure and reporting record

Retain a row per scheduled trial: prompt/trial/job/version IDs, initiated/not-run status, input/config/artifact hashes, timestamps, initial candidate and repair outcomes, every metric verdict, both rubric scores and adjudication, latency, actual token use/cost (or unavailable), error class and evidence links. Measure latency from accepted submission to terminal state, including queue/repair; report timeouts as censored at the recorded bound, not as successful fast responses. Summarize medians/ranges for successful trials separately from all-trial timeout counts; report cost across all initiated trials, including failures.

Use a primary failure stage plus all applicable secondary findings: provider/queue/timeout, no output, schema/reference/unsafe content, unsupported scope, unreachable or unverified ending, launch/runtime error, missing action, wrong ending, undisclosed/unfaithful simplification, or missing review/evidence. An initiated infrastructure-aborted trial remains in N; a trial never submitted is not run and lowers scheduled coverage. Report raw group counts and failures even when a conditional output metric looks favorable. **No trial has been executed and no value in this protocol is an observed result.**
