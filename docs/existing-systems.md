# Existing Systems Comparison

**Review method:** Official product documentation was examined on 22 October 2026. This is a desk comparison of documented workflows, not a hands-on test or a reliability benchmark. “Undocumented” means a capability was not established by the cited pages; it does not prove absence. The detailed system notes and source context are in `docs/existing-systems/`.

We selected **Rosebud AI Game Maker**, **GDevelop with AI Agent**, and **AI Dungeon** because they cover, respectively, natural-language creation of browser games, AI-assisted editing of explicit game rules, and free-form AI narrative interaction. Their output formats and authoring workflows differ, so a total score would be misleading. The nine questions below are the same for all three products. They prioritize the diploma target: a nontechnical author submits a story and receives a bounded, complete 2D browser game with a disclosed mechanic mapping and an explicit ending. AI Dungeon is an adjacent narrative comparator, so a missing visual-game feature is an output-category difference rather than evidence of inferior narrative quality.

## Critical analysis and project rationale

Rosebud is the closest comparator and demonstrates that prompt-to-playable-browser-game creation already exists. GDevelop provides more direct human control over game rules and supports AI feature building inside an editor. AI Dungeon offers extensive narrative freedom but a different, text-based output. Their documented strengths matter: a proposal based only on “AI creates games from text” would not establish a distinct need. [R1][R2][G1][D1]

The proposed diploma project focuses on an **explicit intermediate game specification**, a bounded set of supported 2D mechanics, a **record of simplifications**, and checks for launch, core actions and a reachable ending before publication. The public pages document preview and iteration; GDevelop additionally documents experimental input-driven gameplay tests that its AI can write and run. Automated gameplay testing alone therefore does not distinguish this proposal. The inspected pages do not establish a mandatory publication gate that combines specification validation, replay of a winning path for the supported finite rules, and a user-facing record of mechanic simplifications. This is a **documentation gap in this review**, not proof that competitors lack internal checks. The proposed architecture is a testable research and engineering direction; whether it delivers better fidelity or completion rates remains to be measured with the planned story corpus and baseline.

For the diploma, “complete” should mean that the validated version launches, supports its declared core actions, and has an explicit goal/ending with a retained winning trace for the supported finite rules. A browser replay must check that the runtime follows that trace. This is a proposed acceptance contract, not a result already achieved. The intended contribution is evaluating this contract and its narrative tradeoffs within a small mechanic family; neither a structured representation nor an ending check is claimed as a first-ever invention.

The comparison also constrains scope. GDevelop's guidance to split complex requests and Rosebud's tutorial to start with one small game support a limited first mechanic set. Platformer, racing and card genres remain evaluation cases or future expansion, rather than supported first-version mechanics. [G1][R1]
